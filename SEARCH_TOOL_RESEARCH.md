# Web search for ARIA: provider decision

Checked against providers' own documentation and terms on 20 October 2026. Prices and free allowances can change; verify them again when opening an account. This concerns **public-web search**, not retrieval of a workspace's authorized business data. ARIA must keep those paths separate and must not send private documents, secrets, or customer records as search queries.

## Recommendation

Use **Tavily Search** for the first server-side prototype: its [free Researcher allowance](https://www.tavily.com/pricing) is 1,000 API credits each month with no card, and a [basic search](https://docs.tavily.com/documentation/api-reference/endpoint/search) uses one credit (`advanced` uses two). It returns titles, URLs, and content snippets suitable for citations while ARIA continues generating its own answer with Bedrock. At 500 users, the free allowance is an evaluation budget, not a production budget: one basic search per user per day would be roughly 15,000 credits/month before retries and multi-search answers. Pay-as-you-go is listed at $0.008/credit, or approximately $120 for that 15,000-search scenario, excluding Bedrock and tax. Tavily's [platform terms](https://www.tavily.com/terms) explicitly contemplate integration in customer applications, but ARIA should review those terms before launch, especially the clauses on end-user responsibility, third-party indexes, and use of input. Send only the minimal public query. Do not use Tavily's answer/research AI features for confidential business data without a separate privacy review.

For a production pilot where retention of search-result snippets inside saved ARIA chats matters, **get written confirmation of result-storage/display rights before choosing any provider**. A safe implementation can persist ARIA's original answer and source URL/title while discarding raw provider responses, but even that should be checked against the selected provider's terms. Show source links for factual web claims and label the freshness/limitations of the search.

## Integration boundary

1. Add a `WebSearchProvider` server interface that returns normalized `{title, url, snippet, publishedAt?}` records. Keep the API key in server environment variables; do not expose it in Next.js client code or logs.
2. Let the server, not the browser or model, enforce plan allowance, per-user/workspace rate limits, a monthly search budget, query length, timeout, and maximum result count. Use web search only when the user requests current/public information or clearly needs it.
3. Exclude private workspace content from outbound queries. Keep authorized business-data retrieval on ARIA's separate workspace-scoped path, then combine source sets only at the answer stage with distinct citation labels.
4. Treat returned pages/snippets as untrusted data. Do not follow their instructions. Give Bedrock bounded excerpts and stable source IDs; check that every rendered citation maps to a returned URL. On provider failure, say current web information could not be checked rather than making up a current answer.
5. Before launch, confirm storage/display rights for the chosen provider, add its data handling to ARIA's privacy notice, and measure citation accuracy, latency, and real search consumption on representative user questions.

These prices exclude model tokens, any page extraction, AWS, and taxes. The usage examples are arithmetic estimates, not quotes or reserved capacity.
